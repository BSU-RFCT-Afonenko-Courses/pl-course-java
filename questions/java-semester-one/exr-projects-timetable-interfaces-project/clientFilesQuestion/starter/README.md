<a id="exr-projects-timetable-interfaces-project"></a>

Разработайте приложение, в котором можно составлять и изменять расписание, а затем получать актуальные занятия преподавателя или группы. Операции управления выразите через самостоятельно спроектированные интерфейсы и реализуйте их для общего расписания, школы и автошколы.

Подготовка: классы ([Глава 11](https://bsu-rfct-afonenko-courses.github.io/Java/theory/classes.html#sec-theory-classes)), интерфейсы ([Глава 13](https://bsu-rfct-afonenko-courses.github.io/Java/theory/interfaces.html#sec-theory-interfaces)) и коллекции ([Глава 18](https://bsu-rfct-afonenko-courses.github.io/Java/theory/collections.html#sec-theory-collections)). До реализации выберите небольшое расписание и вручную проследите, как отмена занятия меняет выборку и количество занятий. По этим действиям определите операции интерфейсов.

<div>

<a id="данные-и-операции-1"></a>

#### Данные и операции

</div>

Занятие содержит дату, время, предмет, преподавателя, группу и аудиторию. У предметов, преподавателей и групп уникальные идентификаторы. Сначала задайте два предмета, двух преподавателей, две группы и четыре занятия. Конкретные названия, даты и распределение занятий выберите сами.

Реализуйте все операции:

- создание и удаление расписания;
- создание, изменение и удаление предмета и преподавателя;
- отображение расписания выбранного преподавателя и выбранной группы;
- отображение списков всех предметов и преподавателей;
- изменение аудитории занятия, отмену занятия и добавление дополнительного;
- добавление выходного;
- подсчёт количества занятий выбранного преподавателя и выбранной группы.

Выборки и подсчёты должны отражать текущее расписание после изменений. Для удаления предмета или преподавателя, на которого ссылаются занятия, явно выберите политику. Например, можно отклонять такое удаление до отмены связанных занятий или удалять их вместе с сущностью. Объясните результат выбранного действия. После добавления выходного из действующего расписания исключаются занятия указанной даты согласно выбранной политике.

<div>

<a id="специализации-расписания"></a>

#### Специализации расписания

</div>

Школьное расписание должно поддерживать выборку по классу и проверку числа уроков за день. Расписание автошколы должно различать теоретические и практические занятия и проверять наличие учебного автомобиля для практического занятия. Предел числа уроков и модель автомобилей задайте и объясните самостоятельно.

До наблюдения результатов назовите выбранные политики удаления и выходных, предел уроков и модель автомобилей. Предъявите исходники и продемонстрируйте операции на исходном наборе и после изменений. Сопоставьте выводимые занятия с их количеством; отдельно покажите результат удаления связанной сущности, добавления выходного и проверок обеих специализаций. Типы, интерфейсы, имена и сигнатуры методов проектируются самостоятельно. [\[1\]](#ref-bib-task-timetable-interfaces-project)

<a id="вход-для-воспроизводимой-проверки-1"></a>

#### Вход для воспроизводимой проверки

</div>

Обязательные объявления входа заданы в стартере; сохраните их и свяжите со своим решением. Собственные классы, видимость, вспомогательные методы и алгоритмы выбирайте в пределах условия. Если предметный API уже обеспечивает этот вход, дополнительный класс не требуется.

Самостоятельно спроектируйте интерфейсы управления и реальные модели трёх расписаний. Вход проверки не заменяет эти интерфейсы и не содержит готовых операций управления. Политики удаления и выходного, предел школы и модель автомобилей остаются вашим предварительно объявленным выбором.

<div class="public-tests">

### Открытые примеры

В примере есть два предмета `S1`, `S2`, два преподавателя `T1`, `T2` и две группы `G1`, `G2`. Исходные занятия:

- `L1`: 19 октября, 09:00, `S1`, `T1`, `G1`, аудитория `101`;
- `L2`: 19 октября, 10:00, `S2`, `T2`, `G1`, аудитория `102`;
- `L3`: 20 октября, 09:00, `S1`, `T1`, `G2`, аудитория `101`;
- `L4`: 20 октября, 10:00, `S2`, `T2`, `G2`, аудитория `102`.

Год, названия и идентификаторы выбраны заранее. До изменений выборка `T1` содержит `L1`, `L3`, а выборка `G1` — `L1`, `L2`; оба количества равны `2`. После отмены `L1` остаются соответственно `L3` и `L2`, оба количества равны `1`. Перенос `L3` в выбранную аудиторию `C` меняет аудиторию, сохраняя остальные данные занятия, в том числе преподавателя `T1` и группу `G2`. Порядок выборок свободен.

На независимых исходных состояниях того же примера удаляют `T1`, добавляют выходной 20 октября, проверяют школу на объявленном пределе уроков и после попытки превышения, а также теорию и практику автошколы с доступным и отсутствующим автомобилем. Результат удаления соответствует заранее выбранной политике. Выходной исключает `L3`, `L4`; выборки и числа занятий согласованы. Состояние на пределе отличается от превышения: допустимы отказ в добавлении лишнего урока или выявление превышения после добавления. Отсутствие учебного автомобиля для практики выявляется. Политики удаления и выходных, предел школы и модель автомобилей остаются объявленным выбором.

Если стартер предоставляет отдельный вход для проверки, свяжите его со своим реальным решением. Он получает фактические аргументы и возвращает фактические объекты и результаты. Простую задачу можно выполнить с JDK 25 и любым редактором. Для задач с особой подготовкой или системой сборки следуйте условию и инструкции комплекта. Установка IDE или Gradle и запуск открытых проверок сами по себе не являются условием зачёта. Для предусмотренной комплектом сборки через Gradle нужен установленный Gradle 9.8. Откройте извлечённую папку с `settings.gradle` как Gradle-проект в IDE. Если комплект использует JUnit, зависимость объявлена в `build.gradle`: первое получение требует сети, последующие сборки доступны с `--offline` после заполнения кеша. Особые команды подготовки и сборки, если они нужны задаче, приведены в её условии и локальном дополнении.

Из корня обычного проекта можно выполнить `gradle classes` и, при наличии соответствующих задач, `gradle apiCheck` и `gradle test`. Проверка обязательных объявлений помогает обнаружить несовместимый интерфейс; открытые примеры помогают сопоставить вход и результат. Соблюдение обязательных приёмов, демонстрации и объяснения определяется условием и выбранной лабораторной. Успех самопроверки не заменяет ручную часть. Для независимых компиляционных версий и отрицательных примеров используйте раздельную сборку, указанную в условии или локальном дополнении.

Если программа читает стандартный ввод, запустите `gradle --console=plain -q run`, передайте данные и завершите ввод. Аргументы командной строки передаются отдельно: например, для задачи о сумме и произведении аргументов выполните `gradle --console=plain -q run --args="3 -2 4"`; ввод этих чисел через стандартный ввод аргументы не заменяет. Для собственного демонстрационного класса используйте `gradle --console=plain -q run -PmainClass=ИмяКласса`. Это удобство локального запуска; само по себе оно не назначает имя класса.

Команда `gradle classes` помещает классы решения в `build/classes/java/main`. Для прямого запуска после такой сборки укажите этот путь: например, `java -cp build/classes/java/main Main 3 -2 4` для задачи о сумме и произведении аргументов.

``` sh
mkdir -p out
find src/main/java -type f -name '*.java' -exec javac -d out --source-path src/main/java {} +
```

Команда включает вспомогательные классы во вложенных пакетах. Затем выполните команду запуска из условия, например `java -cp out Main 3 -2 4`. В Windows можно собрать тот же каталог исходников средствами IDE и указать `out` как каталог классов либо воспользоваться запуском через Gradle.
